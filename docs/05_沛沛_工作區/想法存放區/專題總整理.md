# 專題總整理(可延續討論版)

## 1. 專案定位
**經選助手**:給保險業務員的客戶管理系統,Flutter Web,以 Supabase、Vercel、GitHub 部署,要能手機使用(web app)。報告同時要呈現「成果」與「用 AI 做出來的過程」。

## 2. 現況與痛點
- 目前用 Antigravity(Gemini)vibe coding,零花費
- 功能之間常有斷層,規則檔是拼湊的,不確定問題在模型還是規則
- 現有版本視為「莽撞樣品」,只能當參考,不是規格
- 想訂閱 Claude 重新接手。這是可逆的實驗,先訂一個月即可

## 3. 產品功能
- **三大核心**:掃描保單、保單比價、客戶建檔
- **頁面**:客戶列表 → 客戶頁 → 保單頁(現有 / 舊保單)
- **業務流程**:第 1 次 talk 並準備 A、B 方案;第 2 次討論決定,不論 √ △ ×,都要 key 資料
- **拜訪紀錄**:錄音 → 轉字 → 編輯(簡轉繁、補上下文)→ 存檔 → 待辦 → 客戶資料

## 4. 技術與合規筆記
- **前端**:風格統一、手機適手性、斷線提示、載入動畫;質疑現在是不是「假響應式」
- **後端**:Supabase 各部分用途、OAuth 2.0 登入
- **資安**:客戶筆記先去識別化(換成 [客戶A]、[電話1]),送 AI 處理後由後端對照表還原
- **資料來源**:取得方式、爬蟲合法性、版權、並行查詢效能,都待確認
- **部署**:Vercel,另備 Demo 影片

## 5. 待決策(建議順序 1→4)
| # | 決策 | 備註 |
|---|---|---|
| 1 | 功能範圍:必做 / 加分 / 不做 | 決定其餘三項怎麼選 |
| 2 | 資料來源與合法性 | 影響能不能展示 |
| 3 | 是否換掉 Flutter | 評估點:路由網址(go_router)、真響應式、AI 對它的熟悉度 |
| 4 | 是否導入 n8n | 只有需要排程或 LINE 串接才划算,否則 Supabase Edge Functions 就夠 |

## 6. 執行流程
1. **準備**:訂閱一個月、GitHub 建 `legacy` 分支備份、建立 `docs/`
2. **現況盤點**:讓 Claude 掃專案,只產出盤點、不改程式碼,你標記留 / 重寫 / 刪
3. **定義**:需求規格(附驗收標準)、架構與規則檔、3~5 個展示亮點
4. **實作**:一次一個功能,驗收通過才進下一個,每次都寫日誌
5. **測試與部署**:單元、可用性(找人試用)、邊界條件,Vercel 部署並用手機實測
6. **展示產出**:簡報、書面報告、輪播動畫

## 7. 過程紀錄與舉證
- **開發日誌**(每任務一筆):日期 / 工具、任務、提示摘要、來回次數、是否一次到位、人工修補、AI 犯的錯、驗收結果
- **證據**:對話截圖、標明工具的 git commit、新舊版對照
- **差異舉證**:Antigravity 時期當 before,挑 2~3 個任務同需求重做,用同一組指標比較
- **說法**:承認多重變因(規則、需求、工具同時改)、結論保守、拆開「模型帶來的差異」與「我的流程帶來的差異」
- **待查**:Antigravity 本身能否選 Claude 模型,否則要分清是比模型還是比工具

## 8. 報告與簡報結構
- **簡報**:痛點動機 → 解決方案與特色 → 核心技術亮點 → Live Demo → 未來展望與限制
- **AI 過程篇**:初期問題(斷層案例)→ 發現原因 → 調整 → 對照結果 → 反思
- **文件**:需求規格、架構圖 / 流程圖 / ER Model、README、資料來源宣告書
- 講稿口語化,預先標好 Demo 切換點

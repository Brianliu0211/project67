## 🎯 最終修改優先級分類

### 🔴 必修項目 (Must-Fix)
1. **`customers.tags` 與 `customer_tags` 重複**：存在兩套 Tag 系統，建議徹底刪除 `customers.tags`。
2. **RLS / 權限**：確保業務員 A 只能存取自身客戶、拜訪、提醒與日曆資料。
3. **`updated_at` 自動更新**：PostgreSQL UPDATE 不會自動改時間，需掛載 Trigger。
4. **`visit_project_customers` 防重複**：加上 `UNIQUE (visit_project_id, customer_id)`。
5. **`schedule_events` 起訖校驗**：補齊 `CHECK (end_at > start_at)`。
6. **Foreign Key 索引**：補齊關聯欄位 B-Tree Index。
7. **`user_id` 與 `profile_id` 命名統一**：`public` schema 業務資料統一關聯至 `profiles(id)`。

### 🟠 建議修項目 (Should-Fix)
8. **`customer_relationships` 自我指向**：加上 `CHECK (source_customer_id <> target_customer_id)`。
9. **`policy_clauses` 產品唯一識別**：設定 `UNIQUE (company_name, product_name)`。
10. **`insurance_news_topics` 概念混雜**：日後評估將 `daily_overview` 拆至 `insurance_news_daily`。
11. **`tags.name UNIQUE` 過度嚴格**：建議改為 `UNIQUE (category_id, name)` 允許不同分類存在同名標籤（例如客戶分類/VIP vs 客戶來源/VIP）。
12. **Delete 行為明確定義**：確保應用層、視圖與 RLS 統一過濾 `WHERE deleted_at IS NULL`。

## 🔍 15 項模組逐項詳細體檢報告（第二輪）

### ① `customers.tags` 雙重系統矛盾（核心首要建議）
* **現況矛盾**：
  * **系統 A**：`customers.tags` Array（如 `['VIP', '高資產', '朋友']`）
  * **系統 B**：`customers` $\to$ `customer_tags` $\to$ `tags` $\to$ `tag_categories`
* **處方建議**：直接刪除 `customers.tags` 欄位，全面走正規化 `customer_tags` 多對多結構。

---

### ② `tags.name UNIQUE` 限制過嚴
* **現有定義**：`name text NOT NULL UNIQUE`
* **問題**：全系統只能有一個 `VIP`，無法支援不同分類下的同名標籤（如「客戶價值 $\to$ VIP」與「客戶來源 $\to$ VIP」）。
* **處方建議**：
  ```sql
  ALTER TABLE public.tags DROP CONSTRAINT tags_name_key;
  ALTER TABLE public.tags ADD CONSTRAINT tags_category_name_key UNIQUE (category_id, name);
  ```

---

### ③ `visit_project_customers` 重複加入專案
* **現有定義**：僅 `id` 為 Primary Key，允許同一專案重複塞入同一客戶（產生多次關聯）。
* **處方建議**：
  ```sql
  ALTER TABLE public.visit_project_customers 
    ADD CONSTRAINT unique_visit_project_customer UNIQUE (visit_project_id, customer_id);
  ```

---

### ④ `schedule_events` 時間起訖約束
* **問題**：允許開始 `15:00`、結束 `10:00`。
* **處方建議**：
  ```sql
  ALTER TABLE public.schedule_events 
    ADD CONSTRAINT schedule_events_time_check CHECK (end_at > start_at);
  ```

---

### ⑤ `schedule_events` 經緯度範圍限制
* **問題**：`latitude` / `longitude` 無上下限，可填入 `999` 或 `-500`。
* **處方建議**：
  ```sql
  CHECK (latitude IS NULL OR latitude BETWEEN -90 AND 90),
  CHECK (longitude IS NULL OR longitude BETWEEN -180 AND 180)
  ```

---

### ⑥ `user_id` 與 `profile_id` 命名統一
* **現有混用**：
  * `customers.profile_id` $\to$ `profiles.id`
  * `visit_projects.profile_id` $\to$ `profiles.id`
  * `schedule_events.profile_id` $\to$ `profiles.id`
  * 但 `visit_logs.user_id` $\to$ `auth.users.id`
  * `customer_relationships.user_id` $\to$ `auth.users.id`
* **處方建議**：統一將業務表命名為 `profile_id REFERENCES public.profiles(id)`，架構更具一致性：
  $$\text{所有業務資料} \longrightarrow \text{profiles.id} \longrightarrow \text{auth.users.id}$$

---

### ⑦ Supabase RLS 安全性隔離（最高優先級）
* **核心防護**：
  * 業務員 A $\to$ 只能看到自己的 `customers`、`reminders`、`visit_logs`、`schedule_events`。
  * 嚴防登入後執行 `SELECT * FROM customers` 撈出全公司客戶個資。

---

### ⑧ `updated_at` 自動更新 Trigger
* **問題**：`DEFAULT now()` 僅在 INSERT 生效，UPDATE 時不會動。
* **處方建議**：全表掛載 `BEFORE UPDATE` Trigger 呼叫 `update_updated_at()`。

---

### ⑨ `customer_relationships` 禁止自我指向
* **問題**：可建立「王小明 $\to$ 王小明 $\to$ 朋友」。
* **處方建議**：
  ```sql
  CHECK (source_customer_id <> target_customer_id)
  ```

---

### ⑩ `customer_relationships` 防重複關係
* **問題**：同一對客戶可重複建立多次「夫妻」關係。
* **處方建議**：
  ```sql
  UNIQUE (user_id, source_customer_id, target_customer_id, relationship_type)
  ```

---

### ⑪ `policy_clauses` 複合唯一鍵
* **問題**：若無唯一鍵，同一保險公司的同名保單可重複寫入多次。
* **處方建議**：
  ```sql
  UNIQUE (company_name, product_name)
  ```

---

### ⑫ `policy_clauses.tags ARRAY` 評估
* **評估結果**：此處若僅作為單純搜尋標籤（醫療/實支/住院），使用 Array 可以接受；若需與全站標籤大分類聯動，再行關聯化。

---

### ⑬ `insurance_news_topics` 模型職責邊界
* **評估結果**：屬於產品設計層面。若 Topic 是長期主題，每日摘要建議拆出 `insurance_news_daily`；若為每日新聞主題分類，現況可維持。

---

### ⑭ Foreign Key 索引補全
* **處方建議**：為 `profile_id`, `customer_id`, `source_customer_id`, `target_customer_id` 等常查欄位建立 B-Tree 索引。

---

### ⑮ `deleted_at` 軟刪除 (Soft Delete) 設計肯定
* **評價**：採用 `deleted_at` 是 CRM 系統極佳的架構選擇。
* **注意事項**：前端查詢、資料庫 View 與 RLS 需統一過濾 `WHERE deleted_at IS NULL`。

---

## 🏛️ 重要長期架構考量：單人 CRM vs 團隊共同管理

* **現行設計**：`customers.profile_id`（一個客戶屬於單一業務員）。
* **架構師建言**：
  * 若目前產品定位為「業務員個人 CRM」，**維持現有 `profile_id` 是最乾淨、最直覺的設計，不建議為了未知的未來過度設計**。
  * 若未來需要支援「多位業務員共同管理同一客戶」，再演進為 `customer_profiles` 多對多表即可。

---

## 🏁 最終收尾公式

> **「正式模型收尾 = RLS 隔離 ＋ 約束 (Constraints) ＋ 觸發器 (Triggers) ＋ 索引 (Indexes) ＋ 軟刪除 (Soft Delete)」**

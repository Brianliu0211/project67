## A. 給接手 AI 的第一句話

這是一個保險業務 CRM，不是純展示型 Dashboard，也不是只靠 AI 堆功能的專題。使用者首先要能安心管理自己的客戶、保單、拜訪與行程；語音、條款、新聞、關係圖、爬蟲與開發者工具，是為了讓工作更快更可靠。

**不得因為想讓畫面好看、Demo 很炫或省事，而犧牲資料真實性、權限隔離、基本操作直覺或可驗證性。**

## B. 專案目前的決策範圍

### B1. 本階段角色優先序

| 角色 | 本階段定位 | 必須完成的事 | 暫不擴張的事 |
|---|---|---|---|
| 一般業務員 `agent` | 第一優先、Demo 主角 | 客戶 CRM、提醒／行程、拜訪紀錄、保單、標籤、必要的語音輔助 | 看他人資料、管理全域字典、直接操作爬蟲 |
| 開發者 `dev` | 第二優先、維運與展示 | 條款／RSS／新聞／標籤字典管理、必要系統觀測、安全維護 | 沒有實際用途的測試面板、把工程細節暴露給業務員 |
| 主管 `admin` | 保留權限模型 | 保持資料庫和 RBAC 可支援 | 暫不新增完整主管 Dashboard、派單與跨業務監控產品流程 |

### B2. 蘿蔔已確認的原始意圖

1. 專案應能讓業務員日常使用，也能在專題展示時清楚說明價值。
2. 現有功能很多，但部分已因反覆追加而出現 UI、邏輯、資料一致性和可操作性問題。
3. 不全面砍掉重寫；優先採「停下來盤點 → 小幅校正規則 → 分階段整修 → 驗證 → 再繼續」的做法。
4. 文件與程式要能互相對齊；但不能因多份文件重複敘述而互相矛盾。
5. 目前開發與展示聚焦 `agent` 與 `dev`，而非把每一個角色都做滿。

### B3. 決策協定：避免三方想法互相覆蓋

| 問題類型 | 依據／決策者 | AI 的正確行為 |
|---|---|---|
| 功能是否存在、Demo 要展示什麼、角色真正需要什麼 | 蘿蔔 | 先提出選項與影響，等待確認 |
| 現在程式實際做了什麼 | `lib/`、`supabase/`、正式環境 | 以實體證據為準，不把舊日誌當事實 |
| 舊 AI 的理由 | 歷史參考 | 保留可用脈絡，但可指出不再合理之處 |
| 資安、RLS、密鑰、租戶隔離 | 不可退讓工程邊界 | 發現風險先阻擋或提出 P0 修正，不為 Demo 留後門 |
| UI 風格與互動調整 | 蘿蔔確認的規格 | 修明確壞掉處；不要未經確認大改美術或重寫頁面 |

變更分級：

- **A 級，可直接修**：明確漏洞、資料外洩、編譯／測試錯誤、錯表名／錯欄位、死功能、不可操作、硬編碼密鑰。
- **B 級，先提出最小方案**：資料表、Migration、角色權限、跨模組流程、新外部服務、可能影響既有資料的調整。
- **C 級，必須由蘿蔔決定**：刪功能、主管端範圍、資料是否團隊共享、Demo 範圍、成本與付費服務選擇。

## C. 系統實體地圖（以目前工作區為準）

### C1. 技術組成

- 前端：Flutter / Dart，目標支援 Web 與手機 RWD。
- 後端：Supabase Auth、Postgres、RLS、Storage、Edge Functions。
- 外部 AI：Groq／Gemini，使用在轉錄、語意排程或新聞處理等流程。
- 自動化：GitHub Actions（部署、新聞、保險商品爬蟲）。
- 核心文件：`.agents/AGENTS.md`、公共規格、進度表、開發日誌，以及蘿蔔／巨獸的個人想法區。

### C2. 前端主要區塊與目前定位

| 程式區塊 | 對使用者的意義 | 優先檢查點 |
|---|---|---|
| `login_screen.dart`、`reset_password_screen.dart`、`profile_screen.dart` | 登入、帳號、Google 連線、帳號狀態 | Profile 建立與更新是否符合嚴格 RLS；刪帳號是否完整且不誤刪 |
| `home_screen.dart`、`schedule_tab.dart`、`schedule_event_dialog.dart` | 首頁、今日工作、行程月／日視圖 | 行程 CRUD、跨日／重疊、手機操作、資料更新是否整頁重載 |
| `customer_management_tab.dart`、`customer_detail_side_sheet.dart`、`trash_bin_screen.dart` | 客戶核心 CRM、詳情、照片、垃圾桶 | 新增／編輯／刪除／復原、照片、標籤、批次匯入、RLS 隔離 |
| `visit_projects_tab.dart`、`relationship_topology_tab.dart` | 拜訪專案、客戶關係圖 | 關聯方向／權限、空狀態、圖譜是否真正反映資料 |

| `dev_console_screen.dart`、`admin_dashboard_tab.dart`、`dev_god_mode_bar.dart` | 開發者／管理維運 | 是否真的有維運價值、是否僅 dev 可見、不得把假狀態當監控 |
| `voice_recorder_widget.dart`、`voice_scheduler_overlay.dart`、`voice_transcription_service.dart` | 語音轉錄與智慧排程 | JWT 先於任何 AI 呼叫、錯誤提示、額度與檔案大小防護 |

### C3. 資料與服務對照

| 資料／服務 | 主要用途 | 目前已知注意事項 |
|---|---|---|
| `profiles` | 帳號資料、role、status、team、Google 連線狀態 | 高風險表；一般使用者不得升權或刪他人 Profile |
| `customers` | 客戶主資料 | 所有子資料的所有權起點；需與軟刪除、照片、標籤一致 |
| `reminders`、`visit_logs` | 跟進與拜訪歷史 | 所有權應由客戶延伸；`visit_logs` 正確擁有者欄位是 `user_id` |
| `schedule_events` | 行程 | 正確時間欄位為 `start_at` / `end_at`；不得再使用已不存在的 `calendar_events`／`start_time` |
| `visit_projects`、`visit_project_customers` | 拜訪專案與其客戶 | 存取必須由 project owner 延伸 |
| `customer_relationships` | 人脈／轉介紹 | 不可自我連結；owner 必須是當前使用者或受授權 dev/admin |
| `customer_policies`、`policy_clauses` | 個人保單與共用條款字典 | 保單是私有客戶資料；條款是登入者可讀、dev/admin 維護的共用資料 |
| `tag_categories`、`tags`、`customer_tags`、`customers.tags` | 標籤字典與客戶標籤 | 目前存在雙重真相風險；需在 P3 定義唯一來源與遷移方式 |
| `insurance_news_*`、`news_rss_sources` | 新聞與 RSS 來源 | 登入者可讀；來源與內容寫入應只限 dev/admin／受保護後端 |
| Storage `avatars`、`customer-photos` | 個人與客戶照片 | 使用公開 URL 的設計需另行做 Storage 存取稽核；不可只看資料表 RLS |

## D. 現況、已修正方向與部署真相

### D1. 已由程式／先前稽核確認的問題

1. **權限風險**：先前正式環境有 `profiles` 全讀／全刪、可自我改 role，以及部分表格匿名全開的情況。
2. **RLS 疊加風險**：Postgres permissive policy 是 OR 邏輯；只新增安全 policy、沒移除舊 policy 不算修好。
3. **語音額度風險**：語音 Function 必須先驗證 JWT，才可解析請求或呼叫 Groq／Gemini。
4. **爬蟲權限風險**：爬蟲不能公開呼叫；排程使用 `x-crawler-secret`，寫入必須使用 Function 內的 Service Role Key，GitHub 不持有 Service Role Key。
5. **欄位不一致**：資料戰情室曾查詢 `calendar_events.start_time`，已在本機修為 `schedule_events.start_at`，仍需用實際畫面驗證。
6. **帳號清理欄位錯誤**：Profile hard delete 曾用錯 `visit_logs.profile_id`；正確為 `visit_logs.user_id`，已在本機修正，仍需端到端測試。
7. **跨平台測試阻斷**：先前 `flutter test` 會因核心檔案使用 Web-only `dart:html` 而在 VM 測試失敗，尚未完成結構性修復。
8. **假資料／假狀態風險**：部分 dev UI 有看似正常的延遲、狀態或監控文字，需逐項確認是否取自真實資料。

### D2. 安全修補的目前狀態：必須以外部部署回報覆核

工作區目前可見以下相關檔案與變更：

- `supabase/migrations/20260818_database_hardening_final.sql`：預定的唯一正式安全修補 Migration。
- `supabase/functions/transcribe-voice/index.ts`、`voice-scheduler/index.ts`：本機已加入／調整 JWT 防護方向。
- `supabase/functions/crawl-insurance-products/index.ts` 與 `.github/workflows/crawl_insurance_cron.yml`：本機正在加入專用排程 secret 與 Service Role Key 寫入模型。
- 舊 `20260817_database_hardening_stage2.sql`、`20260818_security_stopgap.sql`：不可與 final migration 疊加部署。

**在取得正式環境的 Migration 版本、Function 部署版本、Secrets 確認與多帳號測試結果前，以上全部都只能標記為「本機已準備／待確認」，不是「已上線」。**

### D3. P0 正式部署驗收（不可省略）

- [ ] 只套用 `20260818_database_hardening_final.sql`，不重跑遠端已登記的 Stage 1，也不套用舊 Stage 2／stopgap。
- [ ] 確認 Function Secret：`SUPABASE_SERVICE_ROLE_KEY`、`CRAWLER_CRON_SECRET`。
- [ ] 一般 agent 無法更新自己的 `role`、`status`、`team_id`、`team_name`。
- [ ] 一般 agent 無法讀、改、刪其他 agent 的 Profile、客戶、保單、行程、拜訪資料。
- [ ] 匿名無法讀寫私有資料、RSS、新聞、條款、保單。
- [ ] 無 JWT 呼叫語音 Function 為 401，且沒有外部 AI 呼叫。
- [ ] 無／錯 crawler secret 為 401；一般 agent JWT 為 403；正確 secret 才可排程爬蟲。
- [ ] 部署後列出所有 public tables 的 policy，確認沒有未移除的 permissive policy。

## E. 文件與規則：要修什麼、不要修什麼

### E1. 保留的好原則

- 有重大改動就留下開發日誌與 handoff。
- 變更工具／套件就更新工具包。
- 個人靈感可被 AI 讀取、整理為待辦，但不能被 AI 擅自刪除或覆寫。
- 大型工作先思考 Schema/RLS → 邏輯層 → UI → 驗證。
- 不可用假資料、捷徑 UI 或未實作功能來假裝完成。

### E2. 需要小幅修正的規則方向

1. **由完整互相同步改為 SSOT 向外同步**：
   - AI 工作規則唯一主來源：`.agents/AGENTS.md`。
   - 架構與角色唯一主來源：`docs/00_公共規格/main_spec.md`。
   - 進度唯一主來源：`docs/進度.md`。
   - 其他手冊只摘要並連回主來源，不再抄一整份規則。

2. **完成宣告必須附證據**：標記 `已實作`、`待部署`、`待驗證`、`規劃中`、`已廢棄`，不可混用「已完成」。

3. **快捷指令保留意圖、調整工具依賴**：某些舊規則要求不存在的互動工具時，接手 AI 應以簡潔文字確認取代，不得因工具不可用而跳過安全檢查。

4. **文件更新採最小必要原則**：只有改角色、資料模型、路由、外部服務、公開功能或快捷指令時才同步正式規格；不要為每一行程式改動重寫多份文件。

5. **個人工作區是人類領地**：可新增本文件此類交接成果（已獲蘿蔔授權），不可覆寫既有想法筆記。

## F. 分階段整修工作單

### F0｜安全與正式環境真相

**目的**：關閉資料外洩與 AI 額度濫用，建立遠端資料庫／Migration／文件的一致基線。

**工作**：部署與驗證 D3；比對遠端 Schema 和版本；確認 Storage policy；將驗證結果寫回 `main_spec.md`／進度／開發日誌。

**完成定義**：不是 SQL 存在，而是多帳號及匿名測試均符合預期。

### F1｜業務員核心 CRM 流程

**目的**：讓業務員完成一個完整閉環。

**驗收劇本**：

1. 用一般 agent 登入。
2. 新增一名客戶（含基本資料、備註、照片、標籤）。
3. 新增或更新該客戶保單。
4. 建立提醒與行程，於日／月視圖確認存在。
5. 完成行程／提醒後確認拜訪紀錄出現且 owner 正確。
6. 重新整理網頁，確認資料仍存在、畫面不重置成錯誤狀態。
7. 軟刪客戶、在垃圾桶復原，確認所有關聯行為符合設計。

**優先檢查**：表單錯誤訊息、儲存後 UI 是否立刻同步、空狀態、手機版點擊區域、照片失敗／網路失敗處理。

### F2｜前端穩定、測試與 RWD

**目的**：停止「Web 看似能跑、測試與其他平台全壞」的狀況。

**工作單**：

- 將 `dart:html` 使用點隔離在 Web adapter，或採用跨平台 API，讓 VM test 不直接載入 Web-only 檔案。
- 整理 `flutter analyze`：先處理 error，再處理會造成 null／資源泄漏／死碼的 warning；純 style 最後處理。
- 建立最小測試：登入權限分流、客戶所有權、行程 CRUD、語音未登入拒絕、關鍵 UI smoke test。
- 檢查桌機寬、手機窄、鍵盤與 SafeArea；不只看截圖，要實際完成表單流程。
- 評估 `IndexedStack`、keep-alive 與 optimistic update，避免切頁／CRUD 後重複撈整頁資料。

**完成定義**：所有阻斷測試有綠燈或有明確、被接受的暫緩原因；兩種尺寸可完成 F1 劇本。

### F3｜資料模型收斂

**目的**：消除附加式功能留下的雙重真相。

**首要決策**：`customers.tags`（JSON／陣列形式）和 `customer_tags`（關聯表）不可長期同時作為權威。接手 AI 必須先盤點所有讀寫點，提出資料遷移與回退方案，再由蘿蔔確認。

**其他需盤點**：軟刪除與關聯資料、照片 Storage URL／物件生命週期、保單與條款關聯、行程完成與拜訪紀錄 Trigger、客戶關係的雙向／單向語義。

### F4｜開發者維運與 Demo

**目的**：讓 dev 介面能真的幫忙看系統，不是測試文案集合。

**每一個 dev 功能都必須有**：資料來源、角色授權、操作目的、成功／失敗狀態、無資料畫面、不能誤傷正式資料的保護。

優先項目：RSS 來源管理、保單／條款資料治理、爬蟲最後執行結果與錯誤、基本資料品質檢查。若無真實資料來源，暫時不要顯示「正常」「24ms」等假監控數字。

### F5｜延伸功能（最後）

Google Calendar 同步、循環行程、系統通知、客戶預約、匯出、工作照片、進階 AI 語意分析。每個功能開始前都需指定：誰用、資料權限、失敗策略、外部成本、Demo 是否必要。

## G. 待蘿蔔決定清單

AI 不得自行做決策；可以在準備到該階段時提出 2–3 個有取捨的方案：

1. admin 是否可以看全體業務員客戶資料？若可以，使用情境、紀錄與展示邊界為何？
2. dev 是否等同系統管理者，還是只負責資料來源、條款與維運？
3. 標籤字典目前採「全員可讀、dev/admin 可維護」；未來是否需要業務員個人自訂標籤？
4. 專題最小 Demo 劇本要展示哪些：客戶→行程→拜訪、語音、條款健檢、新聞、關係圖、開發者維運，哪些只展示概念？
5. 外部 AI／Google／地圖／爬蟲是否可接受成本、配額與失敗時的降級方案？

## H. 每次工作的固定輸出格式

接手 AI 必須使用以下格式，避免「看起來做很多，實際不知道改了什麼」：

1. **本次目標**：對應 F0–F5 的一件事。
2. **已驗證現況**：檔案、資料表、畫面、測試或遠端查詢證據。
3. **影響範圍**：哪些角色、流程、資料會受影響。
4. **實際變更**：只列真的已修改內容。
5. **驗證結果**：通過／失敗／尚待部署或人工操作。
6. **未改動事項與原因**：防止誤以為漏做。
7. **下一張最小工作單**：明確、可驗收、不要跨太多模組。

禁止用「已優化」「已完整」「應該沒問題」作為驗收結論。

## I. 給接手 AI 的立即執行順序

1. 讀取本文件與公共規格，不改檔。
2. 讀取 Git status；承認現有未提交變更是既有工作，不能覆蓋或 reset。
3. 取得外部 AI 的正式部署回報；若沒有，先標示安全修補為待確認。
4. 完成 F0 的驗收，更新真相文件。
5. 用真實 agent 帳號跑 F1 劇本，將每個中斷點變成獨立 ticket。
6. 再做 F2、F3、F4；F5 不搶在核心穩定前開始。

---

## J. 交接完成的判斷方式

不是所有勾選框都打勾才叫成功。交接成功是下一個 AI 可以在不猜測、不覆蓋、不用假資料、不反覆問同一件事的情況下，安全地完成下一個最小工作單，並能證明它真的完成。

本文件與 `docs/00_公共規格/AI接手與全域整修總規格.md` 一起使用：前者是蘿蔔視角的完整作戰書，後者是公共規格區的長期工作契約。

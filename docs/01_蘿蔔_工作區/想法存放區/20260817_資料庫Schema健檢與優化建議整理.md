## 🔍 15 項模組逐項詳細體檢報告

### 1. `profiles` 使用者設定檔
* **現有定義片段**：
  ```sql
  CREATE TABLE public.profiles (
    status text NOT NULL DEFAULT 'active',
    role text NOT NULL DEFAULT 'agent',
    id uuid NOT NULL,
    email text NOT NULL UNIQUE,
    ...
    CONSTRAINT profiles_id_fkey FOREIGN KEY (id) REFERENCES auth.users(id)
  );
  ```
* **⚠️ 潛在問題 A（自由文字無約束）**：
  `status` 與 `role` 允許寫入任意字串（例如 `banana`, `super_admin`），資料庫層級無法阻止無效狀態。
  * **處方建議**：
    ```sql
    status text NOT NULL DEFAULT 'active'
      CHECK (status IN ('active', 'inactive', 'suspended')),

    role text NOT NULL DEFAULT 'agent'
      CHECK (role IN ('agent', 'manager', 'admin'))
    ```
* **⚠️ 潛在問題 B（Email 與 Auth 一致性）**：
  同時存在 `auth.users.email` 與 `public.profiles.email`，若未配置同步 Trigger，可能發生 auth 為 `a@gmail.com` 但 profile 顯示 `b@gmail.com` 的資料不同步現象。
  * **處方建議**：若 `profiles.email` 僅為顯示/快取用途，必須有自動同步機制（例如 Auth Hook / DB Trigger）。

---

### 2. `customers` 客戶表
* **現有定義片段**：
  ```sql
  profile_id uuid NOT NULL
  ```
* **⚠️ 潛在問題 A（客戶歸屬與共用情境）**：
  強制 `profile_id NOT NULL` 代表「單一客戶永遠只隸屬單一業務員」。若未來需要支援「A 業務員建立、B 業務員或主管共同檢視/指派」的團隊模式，此單一外鍵模型會產生限制。
* **⚠️ 潛在問題 B（`tags ARRAY` 冗餘設計）**：
  目前同時存在 `customers.tags` (Array) 與多對多關聯結構（`tag_categories` $\rightarrow$ `tags` $\rightarrow$ `customer_tags`）。
  * **衝突情境**：若 `customers.tags = ['VIP']` 但 `customer_tags` 關聯了 `VIP` 與 `高資產`，會造成前端無法判定何者為真。
  * **處方建議**：**徹底刪除 `customers.tags` 欄位**，統一採用標準 Many-to-Many 關聯表：
    $$\text{customer} \longrightarrow \text{customer\_tags} \longrightarrow \text{tag} \longrightarrow \text{tag\_category}$$

---

### 3. `customers.referral_source_id` 轉介紹來源
* **現有定義片段**：
  ```sql
  referral_source_id uuid REFERENCES public.customers(id)
  ```
* **⚠️ 潛在問題（循環介紹風險）**：
  自我參照能表達「王小明 $\rightarrow$ 介紹 $\rightarrow$ 陳小華」，但資料庫無法自動阻止循環參照（如 $A \rightarrow B \rightarrow A$ 或 $A \rightarrow B \rightarrow C \rightarrow A$）。
  * **處方建議**：若系統業務邏輯嚴禁閉環介紹，需在應用層或透過 Trigger 遞迴檢查防止循環。

---

### 4. `reminders` 事項提醒
* **現有定義片段**：
  ```sql
  customer_id, raw_transcript, ai_summary, remind_at, is_completed
  ```
* **⚠️ 潛在問題（缺乏稽核與完成時間維度）**：
  單純使用 `is_completed = true` 無法追蹤「何時完成」、「誰完成的」，降低了 CRM 歷程分析價值。
  * **處方建議**：
    * 新增 `completed_at timestamptz`（完成時填入時間戳，甚至可用 `completed_at IS NOT NULL` 作為完成判斷）。
    * 新增 `created_by uuid` 作為建立人稽核欄位。

---

### 5. `visit_logs` 拜訪紀錄
* **⚠️ 潛在問題 A（外鍵參照對象混用）**：
  `visit_logs` 使用 `user_id uuid NOT NULL REFERENCES auth.users(id)`，但其他業務表均使用 `profile_id REFERENCES public.profiles(id)`。
  * **處方建議**：統一 `public` schema 業務表的命名與參照標的為 `profile_id REFERENCES public.profiles(id)`，維持整體架構一致性。
* **⚠️ 潛在問題 B（`reminder_id` 刪除行為語意不明）**：
  `reminder_id` 未定義 `ON DELETE` 行為。預設會禁止刪除被參照的 reminder。
  * **處方建議**：明確定義業務場景（CRM 通常建議保留歷史拜訪紀錄）：
    * 建議配置 `ON DELETE SET NULL`（提醒被刪除時，拜訪紀錄保留但解除關聯），而非連帶刪除。

---

### 6. `schedule_events` 行事曆事件
* **⚠️ 潛在問題 A（時間起訖未校驗）**：
  `start_at` 與 `end_at` 缺少約束，可能被寫入結束時間早於開始時間的無效資料（例如 `start_at = 10:00`, `end_at = 09:00`）。
  * **處方建議**：
    ```sql
    CHECK (end_at > start_at)
    ```
* **⚠️ 潛在問題 B（`event_type` 自由文字）**：
  預設 `'personal'` 但無枚舉限制。
  * **處方建議**：
    ```sql
    CHECK (event_type IN ('personal', 'customer_visit', 'meeting', 'follow_up'))
    ```
* **⚠️ 潛在問題 C（Google 日曆同步重複問題）**：
  `google_event_id`、`google_calendar_id` 若未加唯一約束，同步程式若重試或並行執行，容易產生多筆重複的 DB 事件。
  * **處方建議**：
    ```sql
    UNIQUE (profile_id, google_calendar_id, google_event_id)
    ```

---

### 7. `visit_projects` 拜訪專案與客戶關聯
* **現有結構**：
  $$\text{visit\_projects} \longrightarrow \text{visit\_project\_customers} \longrightarrow \text{customers}$$
* **⚠️ 潛在問題（多對多未防重複）**：
  `visit_project_customers` 僅以 `id uuid` 為主鍵，未對 `(visit_project_id, customer_id)` 建立唯一性約束，允許同一個專案重複加入同一客戶多次。
  * **處方建議**：
    ```sql
    UNIQUE (visit_project_id, customer_id)
    ```

---

### 8. `insurance_news_topics` 新聞主題與每日摘要
* **現有欄位混合**：`topic_title`, `category`, `publish_date`, `daily_overview`, `daily_trend`
* **⚠️ 潛在問題（概念混雜）**：
  將「長青新聞主題 (Topic: 健保改革/新制保單)」與「每日動態摘要 (Daily Digest: 2026-08-17 今日概覽)」塞在同一張表，模型責任模糊。
  * **處方建議（拆分模型）**：
    1. `insurance_news_topics`：專門存放新聞主題與分類。
    2. `insurance_news_daily`：專門存放每日產出的概覽與趨勢：
       ```sql
       -- insurance_news_daily
       date date PRIMARY KEY,
       daily_overview text,
       daily_trend text
       ```

---

### 9. `insurance_news_articles` 保險新聞文章
* **⚠️ 潛在問題（缺少 URL 唯一性）**：
  `source_url text NOT NULL` 未配置 `UNIQUE`。自動化 RSS 爬蟲或排程爬取時，極易將同一篇文章重複插入多筆。
  * **處方建議**：
    ```sql
    UNIQUE (source_url)
    ```

---

### 10. `policy_clauses` 保單條款庫
* **⚠️ 潛在問題 A（`product_name UNIQUE` 過度嚴苛）**：
  目前設定 `product_name text NOT NULL UNIQUE`。若不同保險公司推出同名商品（例如 A 壽險「安心醫療」與 B 產險「安心醫療」），第二間公司將無法寫入。
  * **處方建議**：改為保險公司與商品名稱的複合唯一索引：
    ```sql
    UNIQUE (company_name, product_name)
    ```
* **⚠️ 潛在問題 B（`benefits_json` 過度依賴 JSONB）**：
  JSONB 適合多變彈性資料，但若未來需要頻繁做條件過濾（如 `住院日額 > 3000`、`等待期 < 30天`），全塞 JSONB 會降低查詢效能與索引便利度。
  * **處方建議**：高頻查詢核心欄位保留結構化欄位，多變細節才放入 JSONB。

---

### 11. `customer_relationships` 客戶人脈關係圖
* **⚠️ 潛在問題 A（重複關係）**：
  未防重複，可能發生多次重複插入「王先生 $\rightarrow$ 夫妻 $\rightarrow$ 李小姐」。
  * **處方建議**：
    ```sql
    UNIQUE (user_id, source_customer_id, target_customer_id, relationship_type)
    ```
* **⚠️ 潛在問題 B（指向自己）**：
  允許建立「王先生 $\rightarrow$ 夫妻 $\rightarrow$ 王先生」之荒謬資料。
  * **處方建議**：
    ```sql
    CHECK (source_customer_id <> target_customer_id)
    ```

---

### 12. `news_rss_sources` RSS 來源管理
* **⚠️ 潛在問題（狀態字串混雜）**：
  `health_status text DEFAULT '200 OK'` 混雜了 HTTP 狀態碼與錯誤訊息，不利於自動化監控與程式邏輯判斷。
  * **處方建議**：拆分為結構化欄位：
    ```sql
    last_http_status integer,
    last_error text,
    last_checked_at timestamptz
    ```

---

### 13. `updated_at` 自動更新機制缺失（致命常犯錯誤）
* **⚠️ 核心問題**：
  許多資料表配置了 `updated_at timestamptz DEFAULT timezone('utc', now())`，但 `DEFAULT` 僅在 **`INSERT`** 時生效。當執行 `UPDATE` 時，`updated_at` **完全不會變更**！
* **處方建議**：建立全域更新函式並套用 Trigger：
  ```sql
  CREATE OR REPLACE FUNCTION update_updated_at()
  RETURNS TRIGGER
  LANGUAGE plpgsql
  AS $$
  BEGIN
    NEW.updated_at = now();
    RETURN NEW;
  END;
  $$;

  -- 分別掛載到各表
  CREATE TRIGGER set_profiles_updated_at
  BEFORE UPDATE ON public.profiles
  FOR EACH ROW EXECUTE FUNCTION update_updated_at();

  CREATE TRIGGER set_customers_updated_at
  BEFORE UPDATE ON public.customers
  FOR EACH ROW EXECUTE FUNCTION update_updated_at();

  -- 同理套用至 reminders, visit_projects, schedule_events 等表
  ```

---

### 14. Supabase Row Level Security (RLS) 安全隔離
* **⚠️ 核心問題**：
  當前 schema 完全未呈現 RLS 政策。若在 Supabase 上線而未開啟 RLS，任何已登入業務員透過 API 呼叫均可能讀取到其他業務員的客戶個資、拜訪紀錄與日程。
* **處方建議**：
  1. 所有業務資料表強制啟用 RLS：`ALTER TABLE public.customers ENABLE ROW LEVEL SECURITY;`
  2. 嚴格制定 4 權限（SELECT / INSERT / UPDATE / DELETE）的 Policy：
     ```sql
     CREATE POLICY "Agents can view own customers"
     ON public.customers
     FOR SELECT
     USING (profile_id = auth.uid());
     ```

---

### 15. Foreign Key 索引補全 (Index Hardening)
* **⚠️ 核心問題**：
  PostgreSQL 建立 Foreign Key **不會自動為該欄位建立 B-Tree Index**。在大資料量下，常態查詢（如 `WHERE profile_id = auth.uid()`、`WHERE customer_id = ...`）會引發全表掃描 (Seq Scan)。
* **處方建議**：為高頻外鍵與過濾欄位建立索引：
  ```sql
  CREATE INDEX idx_customers_profile_id ON public.customers(profile_id);
  CREATE INDEX idx_reminders_customer_id ON public.reminders(customer_id);
  CREATE INDEX idx_visit_logs_customer_id ON public.visit_logs(customer_id);
  CREATE INDEX idx_visit_logs_profile_id ON public.visit_logs(profile_id);
  CREATE INDEX idx_schedule_events_profile_id ON public.schedule_events(profile_id);
  CREATE INDEX idx_customer_tags_tag_id ON public.customer_tags(tag_id);
  ```

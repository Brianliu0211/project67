# AI 接手與全域整修總規格

> **用途**：本文件是接手本專案的 AI／開發者之工作契約。它不是開發日誌，也不是靈感清單；任何跨模組修正都必須先遵守本文件，再讀取對應的程式、Migration 與歷史文件。
>
> **本階段產品焦點**：一般業務員（agent）可完成日常 CRM 工作；開發者（dev）可安全維運與展示系統。主管（admin）保留權限模型，但不是本階段主要 UI 開發對象。
>
> **狀態標記**：2026-08-18 建立。正式 Supabase 的安全 Migration 與 Edge Function 部署結果，必須以部署後驗證報告為準；在取得該報告前，一律視為「待確認」，不得宣稱已上線。

---

## 1. 專案目的與不可偏離的原意

這是一個給保險從業人員使用的 CRM Web／行動應用。它的核心不是展示很多 AI 功能，而是讓業務員更快、更可靠地完成：

1. 建立與維護客戶資料。
2. 記錄拜訪、需求、保單與後續提醒。
3. 安排行程並在需要時以語音減少輸入負擔。
4. 透過條款、新聞、標籤與客戶關係資料輔助判斷。

AI、爬蟲、視覺特效與戰情室都只能支援上述工作；不得為了展示或快速補畫面而破壞資料真實性、資料隔離、可理解性或基本 CRUD。

### 1.1 優先順序

1. **安全與資料正確性**：帳號、客戶資料、RLS、金鑰、資料庫一致性。
2. **業務員工作流可用性**：能直覺完成新增、查看、修改、刪除／復原與追蹤。
3. **可驗證性**：每一項「完成」皆有真實資料、測試方式或可重現操作。
4. **效能與跨裝置體驗**：避免重複讀取、畫面跳動、Web／手機版無法操作。
5. **視覺與展示加分**：在前四項穩定後再處理。

## 2. 決策權與防止三方意圖漂移

| 類型 | 真正決策者 | AI 可以做什麼 | AI 不可做什麼 |
|---|---|---|---|
| 產品目的、展示重點、角色需求 | 蘿蔔 | 提出風險、選項、驗收條件 | 自行改變產品定位或刪除既有能力 |
| 已存在程式／資料庫 | 實體程式與正式環境 | 稽核、指出不一致、提出最小修正 | 把歷史文件當成已實作事實 |
| 資安、RLS、金鑰與資料隔離 | 不可退讓的工程邊界 | 直接提出阻擋風險與安全修正 | 為了 Demo 保留匿名寫入或權限後門 |
| UI／互動細節 | 蘿蔔確認後的規格 | 修正明確壞掉、不可操作、RWD 問題 | 未確認就全面換風格或重寫頁面 |
| 舊 AI 的設計理由 | 歷史參考 | 保留脈絡與可取部分 | 因為「原本就這樣」而忽略錯誤 |

### 2.1 變更分級

- **A｜可直接修正**：漏洞、編譯錯誤、錯表／錯欄位、資料外洩、死連結、明確無法操作、測試失敗。
- **B｜先提出方案再實作**：Schema 調整、角色能力改變、跨模組流程、新增外部服務、影響既有資料的遷移。
- **C｜必須由蘿蔔決定**：功能是否刪除、Demo 主軸改變、主管端產品範圍、資料是否團隊共享、成本／付費服務選擇。

當需求不明確時，AI 必須把「已知事實、假設、可選方案、影響」分開寫；不得把猜測包裝成既定規則。

## 3. 角色邊界與主要使用旅程

### 3.1 一般業務員（agent）— 本階段第一優先

| 旅程 | 必要成果 | 不可違反的資料規則 |
|---|---|---|
| 登入與帳號 | 可登入、登出、重設密碼、編輯自己的基本資料 | 只能讀／改自己的 Profile；不得改 role、status、team |
| 客戶管理 | 搜尋、新增、編輯、軟刪除／復原、查看詳情與照片 | 只能操作自己的 customers 與其附件／關聯 |
| 客戶追蹤 | 標籤、提醒、拜訪紀錄、人脈關係、保單 | 關聯資料的所有權必須由客戶所有者延伸 |
| 行程 | 建立、修改、完成、查看日／月視圖與導航 | 只能操作自己的 schedule_events、visit_projects |
| 語音輔助 | 登入後可轉錄或建立排程；失敗時有可理解訊息 | 未驗證請求不得消耗 Groq／Gemini 額度 |
| 情報與條款 | 查閱已發布的新聞、RSS、條款與標籤字典 | 可讀，不可任意污染團隊共用字典或來源 |

### 3.2 開發者（dev）— 本階段第二優先

開發者介面應服務於「維運、資料治理、展示驗證」，而不是把工程測試資料直接放給一般業務員看。有效能力包括：管理條款、RSS 來源、新聞／標籤字典；檢視必要的系統狀態；安全清理或復原資料。

開發者 UI 每個功能都必須回答三件事：**要看什麼、用來做什麼、做完後如何知道成功**。僅為測試而存在的控制項應移入開發工具、測試帳號或受保護的 dev 區，不得混入一般業務流程。

### 3.3 主管（admin）— 保留、不擴張

資料庫與權限可保留 admin 角色，但在未取得明確產品規格前，不新增主管儀表板、跨人員監控、派單或團隊資料閱讀 UI。任何讓 admin 看見業務員客戶資料的設計，必須先由蘿蔔確認隱私與實際業務需求。

## 4. 系統事實地圖（接手前必讀）

### 4.1 技術與主要邊界

- Flutter／Dart 前端；目標為 Web 與行動裝置 RWD。
- Supabase：Auth、Postgres、RLS、Storage、Edge Functions、排程相關整合。
- 語音：`transcribe-voice` 與 `voice-scheduler`，使用外部 AI 服務，需先驗證 JWT。
- 爬蟲：`crawl-insurance-products`，排程以專用 secret 觸發，寫入必須使用 Edge Function 內的 Service Role Key。
- 自動化：GitHub Actions 可觸發爬蟲；不得硬編碼 URL、Publishable Key、Service Role Key 或任何密鑰。

### 4.2 已確認的高風險修正方向

以下是已稽核出的事實／修正方向，部署狀態另以外部驗證報告確認：

1. `profiles` 曾存在過度寬鬆讀取、刪除與自我升權風險。
2. `customer_policies`、RSS、新聞、條款等曾存在匿名或過度寬鬆寫入規則。
3. 多個 permissive RLS policy 會以 OR 疊加；新政策前必須移除全部舊政策。
4. `voice-scheduler`、`transcribe-voice` 必須在讀取音檔與呼叫外部 AI 前驗證身分。
5. 爬蟲須拒絕無 secret／非 admin-dev 的手動請求，並在缺少 Service Role Key 時安全失敗。
6. 既有資料庫 migration 歷史與遠端實體 Schema 曾不一致；任何新 migration 需先做唯讀預檢。

### 4.3 本次安全修補部署約定

- 預定唯一修補檔：`supabase/migrations/20260818_database_hardening_final.sql`。
- 不重跑遠端已登記的 Stage 1。
- 不與舊 `20260817_database_hardening_stage2.sql`、`20260818_security_stopgap.sql` 疊加部署。
- 部署前確認 Edge Function Secrets 至少含 `SUPABASE_SERVICE_ROLE_KEY`、`CRAWLER_CRON_SECRET`。
- 部署後必做：一般帳號升權阻擋、跨帳號資料隔離、匿名讀寫封鎖、三支 Function 的授權測試。

> 若本段與正式環境驗證結果衝突，以正式環境查詢結果為準，並更新本文件與 `docs/進度.md`。

## 5. 文件與規則治理：保留雙向同步，但取消重複真相

原本的「文件更新要雙向同步」意圖是正確的：避免人與 AI 不知道系統現況。但目前規則過多、重複描述時，反而容易造成版本漂移。

### 5.1 單一真理來源（SSOT）

| 內容 | 唯一主來源 | 其他文件如何處理 |
|---|---|---|
| AI 工作規則與快捷指令行為 | `.agents/AGENTS.md` | 手冊、快捷指令檔只摘要並連回主來源 |
| 系統架構與角色／資料模型 | `docs/00_公共規格/main_spec.md` | 本文件作接手入口，不複製所有細節 |
| 本次接手界線與修復路線 | 本文件 | 開發日誌只記錄當次實際完成事項 |
| 已完成／待辦進度 | `docs/進度.md` | 個人工作區只作靈感來源，不由 AI 任意覆寫 |
| 程式真實行為 | `lib/`、`supabase/` 與正式環境 | 文件不可凌駕實體驗證結果 |

### 5.2 文件更新最小規則

只有在下列情境才需同步文件，避免「為了同步而同步」：

1. 改變角色權限、資料欄位、路由、外部服務或可見功能：更新 `main_spec.md` 與必要進度項。
2. 改變快捷指令的觸發或行為：同步 `.agents/AGENTS.md`、快捷指令手冊與開發手冊。
3. 新增套件、SDK 或外部工具：更新 `docs/工具包.md`。
4. 完成一個可驗收工作單位：新增開發日誌，記錄證據、影響、未完成項與 handoff。
5. 個人工作區筆記是人類領地：AI 可讀取、摘要、提出納入建議；未經指示不得改寫或刪除。

### 5.3 建議的小幅規則修訂

- 將「雙向更新」改為「由 SSOT 向摘要文件同步」，不要要求多個文件彼此完整重寫。
- 所有文件的完成宣告應附上驗證證據，例如測試名稱、手動流程或正式環境查詢日期。
- 明確區分 `已實作`、`待部署`、`規劃中`、`已廢棄`；禁止用單一「已完成」混在一起。
- 大型跨模組工作採四段：Schema/RLS → Service/邏輯 → UI → 驗證；每段可獨立停下來驗收。

## 6. 全域整修計畫與驗收方式

### P0｜安全、資料庫真相與部署閉環

**目標**：關閉資料外洩／升權／AI 額度濫用風險，讓本機 migration、遠端 Schema、文件不再互相矛盾。

**驗收**：Migration 成功；RLS policy 清單無寬鬆殘留；agent 不能升權或看他人資料；匿名不能讀寫私有資料；未登入語音請求不呼叫外部 AI。

### P1｜業務員核心工作流可用性

**目標**：逐頁走完客戶、提醒、行程、拜訪紀錄、保單與標籤，處理卡住、資料不同步、假資料與非直覺操作。

**驗收**：用一個一般帳號可從新增客戶到建立提醒、完成行程、產生拜訪紀錄，再回查資料；重新整理後資料仍正確。

### P2｜前端穩定、RWD 與效能

**目標**：修復 Web-only import 導致的測試問題、Analyzer 警告、重複查詢、整頁刷新、窄螢幕不可操作。

**驗收**：Flutter test／analyze 的問題有明確清單與處置；桌機與手機關鍵流程可操作；CRUD 不需要整頁重載。

### P3｜資料模型收斂

**目標**：釐清 `customers.tags` 與 `customer_tags` 是否雙重真相；定義垃圾桶、照片、保單、客戶關係與標籤字典的唯一資料來源。

**驗收**：每一類資料有唯一權威欄位／表與遷移方案；不再因雙寫造成畫面與資料庫不一致。

### P4｜開發者維運工具與展示品質

**目標**：讓 dev 看見真正有用的 RSS、條款、爬蟲狀態與安全資料治理能力；刪除或隔離純測試控制。

**驗收**：每個 dev 功能有明確角色、操作結果、權限限制與失敗提示。

### P5｜延伸功能

Google Calendar 同步、循環行程、通知、預約、匯出、工作照片、AI 進階語意分析等，皆在 P0–P4 穩定後才排程。

## 7. AI 執行協定（交接後照此工作）

1. 先讀本文件、`main_spec.md`、`docs/進度.md`，再閱讀與任務直接相關的程式／Migration。
2. 先報告「現況證據、影響範圍、最小方案、驗收方式」；涉及 B／C 級變更時等待確認。
3. 不可在未讀取遠端 Schema／既有 migration 前直接寫資料庫 SQL。
4. 不可將未部署或未測試內容寫成已完成；不可用假資料掩蓋後端未完成。
5. 每次修改都做與風險相稱的驗證；失敗必須保留錯誤與原因，不可靜默吞掉。
6. 任何金鑰、帳號、Token、Service Role Key 不得寫入程式、文件、Git 或回覆內容。
7. 若工作發現規格衝突，先新增至「待蘿蔔決定」而非私自選邊；若為安全漏洞，先封鎖風險再回報。

## 8. 待蘿蔔決定的產品問題

以下不是 AI 可自行決定的技術問題；在未決定前不得擴張實作：

1. 主管角色的正式工作內容與可見資料範圍。
2. 開發者是否可跨團隊／跨業務員檢視客戶資料，及其展示／稽核理由。
3. 標籤字典是否完全由 dev/admin 管理；目前安全方向是全員可讀、dev/admin 可寫。
4. 哪些功能是專題 Demo 必須成功展示的最小集合。
5. Google Calendar、通知、預約、AI 語意分析等延伸功能的先後與可接受外部成本。

## 10. 交付格式

每次交付請使用以下固定格式，降低誤解與附加式修補：

1. **本次目標**：一句話，對應 P0–P5。
2. **已驗證現況**：檔案、資料表、畫面或測試證據。
3. **變更內容**：只列實際改動。
4. **未改動的原因**：避免誤以為遺漏。
5. **驗證結果**：通過、失敗、尚未可驗證。
6. **下一個最小工作單**：一個明確、可驗收的下一步。

這份格式比「完成了很多功能」更重要；它讓蘿蔔、AI 與實際程式始終對同一件事說話。
